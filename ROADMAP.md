# Стратегия переносимых продуктов — 15 октября 2026

Это **единственный канонический план развития универсальной библиотеки** `KhDenis/skills`. GitHub Issue фиксирует текущую исполняемую задачу; PR и проверочные команды подтверждают сделанное. Не дублировать этот план в чатах или других roadmap.

**Текущий приоритет:** [Issue #1 — перенос Telegram Archive](https://github.com/KhDenis/skills/issues/1). Не начинать параллельно новые продуктовые модули до проверки текущего шага.

## Принятые решения

1. **Два репозитория, не три.** `KhDenis/skills` — универсальный, публичный, без данных пользователей. `KhDenis/godecor` — приватное прикладное решение, конфигурации, бизнес-процессы и интеграции. Не создавать GoldyCore или новый репозиторий-«платформу».
2. **Продукт != skill.** Продукт — автономный движок с CLI, входными и выходными данными, тестами и установщиком; необязательные UI и API добавлять по спросу. Skill — тонкая инструкция агенту по использованию продукта.
3. **Агент не должен исполнять рутинный цикл.** Долгие операции сохраняют прогресс, возобновляются, выдерживают перезагрузки и по возможности выполняются без Claude/Codex. Минимальный локальный исполнитель предпочтительнее многоуровневой оркестрации.
4. **Переносить из Go Decor по одному, без регрессий.** Сначала проверить имеющуюся реализацию и её действительное применение, перенести универсальное ядро, подключить фиксированную версию обратно, проверить Go Decor. Только потом удалить копии.
5. **Результат доказывается.** Моки ≠ end-to-end проверка. «Готово» означает проверенную установку, тесты, работающий сценарий, опубликованные изменения и отсутствие потерь.
6. **Приватность.** Не переносить в публичный репозиторий сессии Telegram, .env, личные переписки, клиентские данные, файлы, секреты, персональные базы или журналы. Работа с чужими переписками ограничена разрешённым объёмом. Не включать платные API и массовую загрузку без согласования.
7. **Меньше бюрократии.** Здесь стратегия, в Issue — следующая задача, в PR — изменения и результаты. Отдельные отчёты ради отчётов, дублированные планы, очередные архитектуры Bridge не создавать.

**Позднее, по реальному сценарию:** Universal Importer (почта/диски/локальные файлы), Document Studio, общий поиск, небольшой Job Runner и прикладная CRM. Не делать всё сразу.

**Bridge/Fleet:** заморожены, не считать обязательным продуктом и не переносить автоматически. На основании реальной полезности решить, оставить компактные части (исполнение заданий, статусы, восстановление) или полностью отказаться; сначала не ломать активные интеграции.

## Приёмка каждого модуля

- `install` и `doctor` или эквивалентные проверяемые команды; изоляция зависимостей и данных.
- CLI/библиотечный интерфейс с документированными входами/выходами, независимо от Claude/Codex.
- Для длительных задач: `status` и надёжный `resume`; повторный запуск не дублирует уже обработанное.
- Автоматические тесты + демонстрация реального ограниченного сценария с конкретными командами, числами и результатами.
- Совместимость Go Decor, прежде чем удалять старую копию.
- Указаны версия, ограничения, способ отката; в Git отсутствуют личные и клиентские данные.

## Как вести работу, чтобы решения не терялись

**Перед сессией:** прочитать этот файл, активный Issue, текущее содержимое обеих веток `main`. Выбрать **один** ближайший невыполненный пункт Issue; не начинать новый аудит без обнаруженной фактической проблемы.

**После сессии:** оставить опубликованный коммит/PR, команду проверки и её результат, что не проверено, причину блокировки (если есть), следующую конкретную операцию; отметить пункт в Issue только по доказательствам. Неподтверждённые или зависшие задания **не закрывать** и не выдавать за успех. Если сессия прервалась, следующий агент продолжает по Issue и Git, а не по памяти чата.

**Закрытие этапа:** владелец подтверждает результат на реальном примере; PR слит, Go Decor не сломан; только тогда меняем «текущий приоритет» и открываем следующее Issue.

### Следующее действие

Начать **не с нового аудита всей системы**, а с первого пункта [Issue #1](https://github.com/KhDenis/skills/issues/1): сравнить конкретно две версии Telegram Archive и подготовить безопасный перенос. Если доступ к рабочей машине/данным отсутствует, записать точный блокер; не строить новые подсистемы.
